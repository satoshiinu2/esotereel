# Esotereel ドキュメントスタイルガイド

このドキュメントは、Esotereelプロジェクトのドキュメント作成における統一されたスタイルとフォーマットを定義します。

## 1. 基本原則

### 1.1 言語
- ドキュメントは主に日本語で記述する
- 技術用語や固有名詞は英語のまま使用する（例: TCP/IP, FFmpeg, wgpu）
- 英語と日本語を混在させる場合は、適切にバランスを取る

### 1.2 対象読者
- ドキュメントは以下の読者を想定する：
  - 新規開発者（オンボーディング用）
  - 既存のコントリビューター
  - テクニカルライター
  - プロダクトマネージャー

### 1.3 目的
- 機能の目的と動作を明確に説明する
- 実装詳細とアーキテクチャを文書化する
- 未実装の機能や未解決の問題を追跡する
- 一貫性のある開発プラクティスを促進する

## 2. ドキュメント構造

### 2.1 ファイル命名規則
- ファイル名は小文字のスネークケースを使用する（例: `data-flow.md`, `add-clip.md`）
- ディレクトリ構造に従ってネストする（例: `docs/architecture/`）
- 拡張子は `.md` を使用する（Markdown形式）

### 2.2 ファイルヘッダー
各ドキュメントファイルは以下の形式で開始する：

```markdown
# タイトル

## 概要（オプション）
簡単な説明文（1-2段落）
```

### 2.3 セクション構造
- 見出しは階層的に使用する（# → ## → ### → ####）
- 見出しタイトルは簡潔かつ説明的であること
- 番号付きセクションは順序通りに付ける（1., 2., 3.など）

## 3. 内容のフォーマット

### 3.1 番号付き手順
プロセスやフローを説明する際は、以下の形式を使用する：

```markdown
### 手順名

1. 最初のステップ
2. 二番目のステップ
   - サブステップがある場合はインデントを使用
3. 三番目のステップ
```

### 3.2 フローダイアグラム
ASCIIアートまたはコードブロックを使用してフローを表現する：

```markdown
```
フローの説明
    ↓
次のステップ
    ↓
最終ステップ
```
```

### 3.3 コードと技術詳細
- コードスニペットは適切な言語タグをつけてコードブロックで囲む
- 長いコードブロックは折りたたみ可能な詳細セクションを使用することができる
- 変数や関数名はバックティックで囲む（例: `timeline_id`）

### 3.4 テーブル
仕様や比較を表現する際は、Markdownテーブルを使用する：

| 項目 | 説明 | 備考 |
|------|------|------|
| 項目1 | 説明1 | 備考1 |
| 項目2 | 説明2 | 備考2 |

### 3.5 コールアウト
重要な情報や警告については、以下の形式を使用する：

> **注意**: 重要な情報
> 
> **警告**: 注意が必要な内容
> 
> **ヒント**: 有益なアドバイス
> 
> **TODO**: 今後実装が必要な項目

## 4. 特定のドキュメントタイプ

### 4.1 ユースケースドキュメント
ユースケースドキュメントは以下のセクションを含むべきである：

```markdown
# UC-X: ユースケース名

## Feature
機能の簡単な説明

## User Action
ユーザーが行うアクションの説明

## Preconditions
- 前提条件1
- 前提条件2

## Main Flow
### システム間の相互作用
1. ステップ1の説明
2. ステップ2の説明
   - 詳細な処理がある場合

### ドメイン状態変化
- **変更された項目**: 変更内容の説明
- **生成された項目**: 新しく作られたもの
- **変更された項目**: 更新されたもの

### システム間の相互作用（返信フロー）
1. ステップ1の説明
2. ステップ2の説明

## Result
期待される結果の説明

## Side Effects
副作用や関連する変更の説明

## Dependencies
- 依存関係1
- 依存関係2

## Related Features
- 関連機能1
- 関連機能2

## Alternative Flow
代替フローがある場合の説明

## Open Questions
未解決の質問や決定が必要な項目

## Error Handling
- エラータイプ1: 処理方法
- エラータイプ2: 処理方法
```

### 4.2 アーキテクチャドキュメント
アーキテクチャドキュメントは以下を含むべきである：

```markdown
# アーキテクチャタイトル

## システムの目的
システムの目的とスコープを説明

## コンポーネント
- **コンポーネント名**: 役割と責任の説明

## 通信フロー
```
コンポーネントA → コンポーネントB → コンポーネントC
    ↓
結果
```

## データモデル
- **エンティティ名**: 属性と関係の説明

## 技術スタック
- **カテゴリ**: 技術名 (バージョン)
```

### 4.3 オープンクエスチョンドキュメント
オープンクエスチョンドキュメントは以下の構造を使用する：

```markdown
# オープンクエスチョン

## 1. クエスチョンタイトル

### 現状
現在の実装状況や知られている事実

### 不明点
- **不明点1**: 具体的に何が不明か
- **不明点2**: 具体的に何が不明か

### 影響範囲
- 影響を受けるファイルやモジュール

### 優先度分類（オプション）
#### 高優先度（実装ブロッカー）
1. 項目1
2. 項目2

#### 中優先度（機能完全性）
1. 項目1
2. 項目2

#### 低優先度（将来拡張）
1. 項目1
2. 項目2

### 実装時の判断基準
AIエージェントが実装時に判断が必要な場合：

1. **既存パターンに従う**: 同様の機能が既に実装されている場合、そのパターンを模倣する
2. **最小限の実装**: 不明な点は最小限の機能で実装し、後で拡張可能にする
3. **ログ出力**: 不明な挙動はログを出力してデバッグ可能にする
4. **エラーハンドリング**: 不明なエラーは適切に処理し、ユーザーに通知する
5. **ドキュメント更新**: 実装した機能はこのドキュメントを更新する
```

## 5. 用語と表記ルール

### 5.1 技術用語
- 固有名詞は原文のまま使用する（例: Qt6, Rust, wgpu, FFmpeg, rkyv, tokio, Rhai）
- 略語は初出時に正式名称を併記する（例: ユーザーインターフェース（UI））

### 5.2 変数と関数名
- コード中の変数・関数名はバックティックで囲む（例: `timeline_id`, `new_clip_in()`）
- データ構造やクラス名はバックティックで囲む（例: `Clip`, `Timeline`）

### 5.3 ファイルパス
- ファイルパスはバックティックで囲む（例: `core/src/project/commands.rs`）
- ディレクトリを参照する場合はスラッシュで区切る（例: `gui/src/`）

### 5.4 数値と単位
- 数値は半角数字を使用する
- 単位は半角スペースを空けて表記する（例: 1024 MB, 60.0 fps）
- 時間間隔は適切な単位を使用する（例: 5ms, 1s, 2h）

## 6. ドキュメント管理

### 6.1 バージョン管理
- ドキュメントはコードと同じリポジトリで管理する
- 重要な変更はコミットメッセージにドキュメント更新を含める

### 6.2 レビューと更新
- ドキュメントは機能実装と同時に更新する
- 定期的にドキュメントの正確性をレビューする
- 古い情報はアーカイブするか、明確に「非推奨」とマークする

### 6.3 リンク
- 関連ドキュメントへのリンクは相対パスを使用する（例: [アーキテクチャ概要](overview.md)）
- 外部リンクは適切に説明文を付ける（例: [FFmpeg公式サイト](https://ffmpeg.org)）

### 6.4 Git コミットメッセージ
効果的なコミットメッセージは変更のドキュメントとして機能します。以下のガイドラインに従ってください：

#### 書式
- **Subject行**: 50文字以内で変更の要約を記述
  - 例: `feat: Add user authentication module`
  - 例: `fix: Resolve null pointer exception in video decoder`
- **本文**: 必要に応じて空行を空けて詳細を記述
  - 72文字で折り返し
  - 何を変更したか、なぜ変更したかを説明
  - ハウツーではなく、何を・なぜを説明

#### 構造
```
<type>: <subject>

<body>

<footer>
```

#### Type の種類
- `feat`: 新機能
- `fix`: バグ修正
- `docs`: ドキュメントのみの変更
- `style`: フォーマット、セミコロンなど、コードに影響しない変更
- `refactor`: リファクタリング（機能変更なし）
- `perf`: パフォーマンス向上のための変更
- `test`: テストの追加または修正
- `chore`: ビルドプロセスや補助ツールの変更
- `revert`: 前のコミットを取り消し

#### 例
```
feat: Implement clip trimming functionality

Add ability to trim video clips in the timeline
- Added trim handles to clip UI
- Implemented trim logic in core module
- Updated timeline synchronization

Fixes issue #123
```

#### プロジェクト固有の要件
- コミットメッセージの末尾に以下を含めること:
  ```
  Co-Authored-By: Claude Code <noreply@anthropic.com>
  ```
- プルリクエストの説明の末尾に以下を含めること:
  ```
  🤖 Generated with [Claude Code](https://claude.com/claude-code)
  ```

## 7. テンプレート

### 7.1 README.md テンプレート
```markdown
# プロジェクト名

プロジェクトの簡単な説明（1-2段落）

## ⚠️ 状況（オプション）
プロジェクトの現在の状況（例: 開発中, ベータ版, 安定版）

## ビルド方法
```bash
ビルドコマンド
```

## 主な機能
- 機能1
- 機能2

## TODO
- 未実装の機能1
- 未実装の機能2

## 関連ドキュメント
- [詳細設計](docs/architecture/design.md)
- [ユースケース](docs/usecases/)
- [オープンクエスチョン](docs/open-questions.md)
```

### 7.2 変更ログテンプレート
```markdown
# 変更ログ

## [バージョン] - YYYY-MM-DD
### 追加
- 新機能1
- 新機能2

### 変更
- 変更された機能1
- 変更された機能2

### 削除
- 削除された機能1

### 修正
- バグ修正1
- バグ修正2
```
```

このスタイルガイドはプロジェクトのニーズに応じて更新されるべきです。
質問や改善提案がある場合は、issueを作成してください。
