# プラグイン開発ガイド: 概要

## 概要

Esotereel の機能拡張はプラグインで行います。このドキュメント群は、プラグイン開発者向けのガイドです。

- [概要](overview.md)（本書）: プラグインの全体像、構成、読み込みの仕組み
- [コンポーネント定義リファレンス](components.md): `components/` の TOML、capability、プロパティスキーマ、フック
- [スクリプト API リファレンス](script-api.md): Rhai スクリプトから使える API
- [チュートリアル: 新しいクリップ種別を追加する](tutorial.md): 標準プラグインを題材にした実践手順

## 1. 設計方針

プラグインまわりは、以下の分担を前提に設計されています。

- **描画 API は lib が定義する**: テクスチャ取得や描画コマンドなどの API は lib 側（`lib/src/plugin/`）が定義し、ホスト（core / GUI）が実行環境を提供します
- **描画そのものはプラグイン側が行う**: 「何を描くか」はプラグインの Rhai スクリプトが決め、ホストはその結果（頂点バッチ）を受け取って表示します
- **参照は ID のハードコードではなく能力（capability）経由で行う**: 本体はプロパティ ID やメンバー名を直接知らず、コンポーネントが宣言した capability から参照を逆引きします。プラグイン側もこの規約に従ってください（詳細は [コンポーネント定義リファレンス](components.md)）

## 2. プラグインのディレクトリ構成

プラグインは 1 つのディレクトリで構成されます。標準プラグイン（`plugins/std/`）の構成は次のとおりです。

```
<plugin_dir>/
├── manifest.toml       # プラグインのメタ情報（必須）
├── settings.toml       # 設定項目のスキーマ（任意）
├── clips/              # クリップ種別の定義（任意）
│   └── *.toml
├── components/         # コンポーネント定義とそのスクリプト（任意）
│   ├── *.toml
│   └── *.rhai
├── shaders/            # シェーダ定義と WGSL ソース（任意）
│   ├── *.toml
│   └── *.wgsl
├── toolbars.toml       # ツールバーボタンの定義（任意）
├── buttons/            # ツールバーボタン用スクリプトの置き場（慣例）
│   └── *.rhai
└── script.rhai         # プラグイン共通スクリプト（任意）
```

`manifest.toml` 以外のファイル・ディレクトリはすべて任意です。存在しないものは空として扱われます。

配置場所は次の 2 か所で、配下の各サブディレクトリが 1 プラグインとして探索されます。

- アプリ同梱の組み込みプラグイン: インストールディレクトリ配下の `std_plugins/`
- ユーザープラグイン: ユーザーデータディレクトリ配下の `plugins/`

## 3. manifest.toml

プラグインのメタ情報を記述する必須ファイルです。

```toml
id = "std"
name = "The Standard Plugin"
version = "0.0.1"
```

| フィールド | 型 | 必須 | 説明 |
|------------|------|------|------|
| `id` | 文字列 | ○ | プラグイン識別子。すべての名前空間付き ID の接頭辞になります |
| `name` | 文字列 | ○ | プラグインの表示名 |
| `version` | 文字列 | ○ | プラグインのバージョン |

## 4. 名前空間付き ID（NamespacedID）

プラグインが提供するクリップ種別・コンポーネント・ツールバーボタンは、すべて `plugin_id:local_id` 形式の名前空間付き ID で識別されます（例: `std:video`）。

- TOML 内ではローカル ID だけを書き、読み込み時にプラグイン ID が補われます
- 使用できる文字は ASCII 英字・数字・`.`・`_`・`-`（および区切りの `:`）です。これ以外を含む ID は読み込み時にエラーになります
- ID は全プラグインを通じて一意でなければなりません。クリップ種別やコンポーネントの ID が他のプラグインと衝突すると、インデックス構築時にエラーになります
- プロパティは ID 本体ではなく「所有コンポーネントの ID + コンポーネント内ローカル名」で識別します。正規形のアドレスは `std:media#media`（メンバーまで含めると `std:media#media/source`）です。詳細は [コンポーネント定義リファレンス](components.md) 第 5.3 節を参照してください

## 5. 読み込みの仕組み

プラグインは `PluginLoader`（`lib/src/plugin/mod.rs`）が読み込みます。

1. 組み込み・ユーザーの両配置場所からプラグインディレクトリを探索する
2. 各プラグインを並列に読み込む。**1 つのプラグインの読み込み失敗が全体を止めることはなく**、失敗したプラグインはログに記録されて除外されます
3. 全プラグインのクリップ種別・コンポーネント定義・シェーダ定義・スクリプト・設定スキーマ・ツールバーをマージし、インデックスを構築する

実行時には、プラグインの追加読み込み（ホットロード）、再読み込み、アンロードも API として用意されています。

各定義ファイルの読み込み規則は共通です。

- `clips/` と `components/` は配下のすべての `.toml` ファイルがファイル名順に読み込まれます
- `shaders/` は配下の `.toml`（1 ファイル 1 シェーダ定義）がファイル名順に読み込まれ、WGSL は読み込み時にコンパイル・検証されます（詳細は第 7 節）
- 同一プラグイン内で ID が重複するとエラーになります
- スクリプト（`.rhai`）はコンパイル時に周辺ファイルとマージされます。マージ規則は [スクリプト API リファレンス](script-api.md) を参照してください

## 6. クリップ種別とコンポーネントの関係

クリップ種別（`clips/*.toml`）とコンポーネント（`components/*.toml`）は役割が分かれています。

- **クリップ種別**: タイムラインに配置できるクリップの種類そのものの宣言です。定義は最小限で、プロパティは持ちません
- **コンポーネント**: クリップの描画・振る舞いとプロパティスキーマを提供する部品です

両者は **クリップ種別が宣言するコンポーネント列で結びつきます**。クリップ種別は `components` フィールドに、構成するコンポーネントの ID を宣言順に列挙します。クリップ種別 `std:video` のプロパティと描画は、コンポーネント `std:media` と `std:transform` が提供します。コンポーネントはクリップ種別から独立した部品であり、複数のクリップ種別から再利用できます。

コンポーネント定義の詳細は [コンポーネント定義リファレンス](components.md) を参照してください。

## 7. シェーダ

シェーダは `shaders/` ディレクトリに置く独立要素です。メタデータ TOML（1 ファイル 1 定義）と WGSL ソースの組で宣言し、コンポーネント等からは名前空間付き ID（例: `std:wave_compute`）で参照します。

```toml
id = "wave_compute"
name = "Wave (Compute)"
source = "wave_compute.wgsl"
kind = "compute"
entry_compute = "deform_main"

[[properties]]
key = "core:time"

[[properties]]
key = "amplitude"
label = "Amplitude"
kind = { type = "float", min = 0.0, max = 100.0, step = 0.1 }
default = 10.0
```

| フィールド | 型 | 必須 | 説明 |
|------------|------|------|------|
| `id` | 文字列 | ○ | シェーダのローカル ID |
| `name` | 文字列 | ○ | 表示名 |
| `source` | 文字列 | ○ | `shaders/` からの相対 WGSL ファイル名 |
| `kind` | 文字列 | ― | `"compute"` のとき compute 用。省略時は render 用 |
| `entry_vertex` / `entry_fragment` | 文字列 | render 用は ○ | render 用シェーダのエントリポイント |
| `entry_compute` | 文字列 | compute 用は ○ | compute 用シェーダのエントリポイント |
| `properties` | 配列 | ― | パラメータ宣言（下記） |

`properties` は宣言順に Params uniform へ詰められます。各項目はコンポーネントのプロパティスキーマと同じ `key` / `label` / `kind` / `default` の表記を使います。`key` が `core:` で始まる項目は lib が値を供給する共通パラメータで、型は lib 側で固定のため `kind` / `default` は書けません（書くと読み込みエラーになります）。既知の `core:` パラメータは次のとおりです。

| キー | 型 |
|------|------|
| `core:time` | `f32` |
| `core:screen_size` | `vec2<f32>` |
| `core:view_projection` | `mat4x4<f32>` |
| `core:transform` | `mat4x4<f32>` |

WGSL は wesl でモジュール解決されます。`shaders/` 配下の `.wgsl` / `.wesl` ファイルは `package::` モジュールとして登録され、自プラグイン内のモジュールを `import package::...` や相対 import で参照できます。また、lib が提供する `core::common` モジュール（頂点定義 `ClipVertex` と `CLIP_VERTEX_FLOATS`）を `import core::common::CLIP_VERTEX_FLOATS;` のように取り込めます。読み込み時に wesl 解決と naga 検証を行い、失敗した場合はそのプラグイン全体の読み込みがエラーになります（他プラグインには影響しません）。

compute シェーダはクリップの「シェーダスタック」に載せて使います。スタックはクリップが保持する順序付きリストで、各エントリはシェーダ参照（名前空間付き ID）と、そのシェーダ固有プロパティの値の組です。描画時にはスタック先頭から順に compute パスが適用され、変形済みの頂点が通常のパイプラインで描画されます（変換行列は変形後に 1 回だけ適用されます）。`core:` パラメータには、`core:time` としてクリップのメディア時刻、`core:transform` としてバッチの変換行列、`core:view_projection` と `core:screen_size` としてフレーム共通の値が lib から供給されます。

**現在の実装範囲**: シェーダ定義の読み込み（TOML パース、wesl コンパイル、naga 検証、レジストリ登録）、compute 用の Params パッキング（宣言順に uniform バイト列を生成）とスタック実行ランナー（頂点バッファを storage buffer に置き、シェーダ 1 つ = compute パス 1 回で ping-pong 適用）、およびクリップのシェーダスタックと実レンダーループへの接続が実装済みです。render 用シェーダの実行配線と、GUI でのスタック編集は未実装です。
